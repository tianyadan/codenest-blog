# 并发秒杀系统设计：从数据库行锁到 Redis + MQ 削峰

秒杀的本质不是“把下单接口写得更快”，而是在极短时间内，把绝大多数无效请求挡在热点路径之外，同时保证库存不超卖、订单最终能落库。

最近整理了一套可演进的秒杀设计：并发不高时先用数据库行锁；压力上来后，把库存扣减迁到 Redis；订单创建交给 MQ 异步完成；前端先展示抢购成功，再轮询订单是否创建完成。

---

## 一、先认清秒杀的核心矛盾

秒杀通常有三个硬约束：

1. **库存不能超卖**：卖 100 件就不能落 101 单。
2. **热点写极高**：同一商品、同一库存字段会被海量请求同时改。
3. **用户体验要快**：接口不能卡死，也不能让用户长时间不知道结果。

数据库擅长事务和一致性，但不擅长扛瞬时写高峰。一旦秒杀热路径直接打 DB，连接池、行锁等待、磁盘 IO 都会很快成为瓶颈。

所以设计重点是：

- **热路径尽量只碰内存**（Redis）
- **慢路径异步化**（MQ 落订单、写 DB）
- **前端接受最终一致性**（先抢成功，再等订单就绪）

---

## 二、阶段一：数据库行锁（并发不高时够用）

当并发只有上千级别时，最直接的方案是数据库行锁 / 乐观锁：

```sql
-- 乐观锁示例：只有库存仍足够时才扣减成功
UPDATE product_stock
SET stock = stock - 1, version = version + 1
WHERE product_id = #{productId}
  AND stock >= 1
  AND version = #{version};
```

或者用 `SELECT ... FOR UPDATE` 做行锁，保证同一商品库存串行扣减。

**优点**

- 实现简单，一致性强
- 适合中小流量活动、内部压测、早期版本

**缺点**

- 热点行锁冲突明显
- DB 连接和事务开销大
- 并发继续升高后，系统会先卡在数据库，而不是业务逻辑

结论很明确：**上千并发可以先用 DB；要冲更高并发，就必须把库存扣减从 DB 挪走。**

---

## 三、阶段二：Redis 预扣库存（热路径禁止碰 DB）

高并发秒杀的关键原则：

> 热路径禁止操作数据库。操作 DB，并发就上不去。

完整热路径大致是：

```text
请求进入
  → 查 Redis 库存（先过滤明显无货）
  → Redis 扣库存（扣减时再校验是否 < 0）
  → 扣减成功后投递 MQ 下单消息
  → 立即返回“抢购成功（处理中）”
```

### 1. 扣库存前先查一次

先读库存，可以把大量“已经没货”的请求快速挡掉，减少无意义写操作：

```text
GET seckill:stock:{productId}
```

如果库存已经 `<= 0`，直接返回售罄。

### 2. 真正扣减时再校验一次

“先查再扣”不是原子的，必须在扣减动作里再次保证不会减成负数。推荐用 Lua 做原子判断：

```lua
-- KEYS[1] = 库存 key
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
  return -1
end
return redis.call('DECR', KEYS[1])
```

伪代码理解：

1. 读取当前库存
2. 若已无库存，返回失败
3. 否则 `DECR`，并再次确认结果不会落到无意义负数（由脚本原子保证）

这样就把“查库存 + 扣库存”合成一次原子操作，避免超卖。

### 3. 为什么这一步不能写 DB

秒杀峰值时，真正贵的不是“生成订单 SQL”，而是：

- DB 连接争用
- 热点行锁等待
- 磁盘刷写放大
- 事务提交延迟

只要热路径还在同步写库，Redis 再快也会被 DB 拖死。因此：**库存预扣在 Redis 完成；订单落库放到异步链路。**

---

## 四、阶段三：MQ 异步下单，解耦削峰

库存扣减成功后，不要同步创建订单，而是发一条下单消息：

```text
Redis 扣库存成功
  → 发送 OrderCreate 消息到 MQ
  → 立即响应前端“抢购成功”
  → 消费者异步：写订单表、写明细、记日志、触发后续流程
```

MQ 在这里承担两个作用：

1. **解耦**：秒杀接口只负责“抢资格”，订单服务负责“落单”
2. **削峰**：瞬时流量先进入队列，消费者按自身吞吐慢慢消化

需要注意的工程细节：

- **消息要带业务幂等键**（如 `userId + productId + requestId`），防止重复消费重复下单
- **扣库存成功但发 MQ 失败**时，要有补偿：回补库存，或落本地消息表重试
- **消费者写 DB 失败**时，按幂等重试；最终失败再回补库存并标记抢购失败

也就是说：前端看到的“抢购成功”，更准确地说是“已获得下单资格，订单正在创建中”。

---

## 五、前端交互：先成功反馈，再轮询订单

为了让用户尽快感知结果，前端可以这样设计：

1. 用户点击秒杀
2. 后端返回“抢购成功 / 处理中”
3. 页面先展示成功态（或排队创建中）
4. 每隔 **1～2 秒** 轮询一次订单状态接口
5. 订单创建完成后，跳转付款页

轮询伪流程：

```text
POST /seckill/grab
  ← { status: "SUCCESS_PENDING", requestId: "xxx" }

每 1~2 秒：
GET /seckill/order-status?requestId=xxx
  ← { status: "CREATED", orderId: "o123" }
  → 跳转 /pay?orderId=o123
```

这种体验比“卡住等同步下单”更友好，也更符合高并发下的最终一致性模型。

可选优化：

- 轮询加最大次数，超时提示“订单生成较慢，请到订单中心查看”
- 有条件时可用 WebSocket / SSE 推送，减少无效轮询

## 六、Redis 容量大致怎么估

经验上可以这样理解：

- Redis 读写并发同时打到 **1～2 万**，单机压力已经不低
- **单 Redis** 常见可扛大约 **2～3 万** 读写并发（和机型、命令复杂度、网络、value 大小强相关）
- 要冲 **10 万级** 并发，通常需要 **Redis 集群**，把热点拆分到多节点

因此架构演进往往是：

```text
单机 Redis（验证链路）
  → Redis 主从 / 哨兵（高可用）
  → Redis Cluster（水平扩展吞吐）
```

热点商品还要注意“单 key 热点”：一个商品库存 key 可能打爆单个分片。必要时可做库存分桶，例如：

```text
seckill:stock:{productId}:0
seckill:stock:{productId}:1
seckill:stock:{productId}:2
...
```

请求按用户或随机桶扣减，汇总后仍等于总库存。

---

## 七、推荐的完整链路

把上面几层串起来，就是一套可落地的秒杀主流程：

```text
用户请求
  → 限流 / 防刷 / 登录校验
  → 读 Redis 库存（快速失败）
  → Redis 原子扣库存（防超卖）
  → 投递 MQ 异步下单
  → 返回“抢购成功（处理中）”
  → 前端轮询订单状态
  → 订单创建完成 → 跳转支付
  → MQ 消费者写 DB（订单落库）
```

对应职责划分：

| 环节 | 职责 | 是否在热路径 |
| --- | --- | --- |
| 网关 / 限流 | 挡恶意流量 | 是 |
| Redis 库存 | 预扣资格、防超卖 | 是 |
| MQ | 解耦削峰 | 是（只发消息） |
| 订单服务 | 落库、生成可支付订单 | 否（异步） |
| 前端轮询 | 等待最终结果并跳转支付 | 客户端 |

---

## 八、小结

这套秒杀思路可以概括成四句话：

1. **低并发先用数据库行锁**，保证正确、落地快。
2. **高并发把库存扣减放到 Redis**，热路径禁止同步写 DB。
3. **扣库存要“先查 + 原子再校验”**，避免超卖。
4. **订单用 MQ 异步创建**，前端先反馈成功，再轮询跳转支付。

秒杀不是单一技术点，而是一致性、吞吐和体验三者之间的取舍。先把主链路想清楚，再逐步补限流、幂等、补偿和分片，系统才会既快又稳。
