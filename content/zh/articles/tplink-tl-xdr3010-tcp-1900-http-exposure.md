# TL-XDR3010 的 TCP 1900 接受了 HTTP 管理请求

家里这台 TP-LINK TL-XDR3010 易展版，本来只想在局域网里看它开了哪些端口。1900 这个数字很眼熟，一般是 SSDP / UPnP，而且走 UDP。这台设备上 TCP 1900 也能连上，并且按 HTTP 把请求接了进去，路径还是 Web 管理里常见的 `/stok=` 形式。这件事值得记下来，但现在还不能叫漏洞。认证有没有被绕过、配置能不能被改、命令能不能被执行，都还没证实。

测试只在我自己的路由器、自己的局域网上做，用的是普通 HTTP 探测。下面的地址写成 `<ROUTER_LAN_IP>`，实际就是这台设备的 LAN 管理地址。

## 端口会说话，但说的不是 SSDP 🔍

对 LAN 管理地址发了一个明显不是合法会话的请求：

```bash
curl -v "http://<ROUTER_LAN_IP>:1900/stok=abc"
```

`stok` 是 TP-LINK Web 管理里用来带 Session Token 的路径段。这里的 `abc` 不是登录后拿到的令牌，只是用来看这个端口会不会把 HTTP 请求交给管理逻辑。连接能建立，请求也被按 HTTP 接受了。

常见情况和这台设备上看到的不一样。SSDP 多半是 UDP 1900，用来做设备发现，不负责路由器的配置接口。这里是：

```text
TCP 1900
    ↓
HTTP 请求
    ↓
/stok=...
    ↓
设备内部的 Web / 管理逻辑
```

所以 TCP 1900 上多半还跑着一套 HTTP 服务，而且和原有的管理接口共用了 stok 这套路径习惯。它是不是独立进程、和 80 端口的管理页是不是同一套代码，现在还不知道。

## 现在能说的，和还不能说的

能确认的只有这条链：

```text
TL-XDR3010
    ↓
<ROUTER_LAN_IP>:1900
    ↓
TCP 连接成功
    ↓
接受 HTTP 请求
    ↓
存在 /stok=... 这种路径
```

还不能确认的有这些：无效 stok 是否仍能碰到需要登录的接口，诊断功能的参数有没有进到系统命令，配置能否被修改，敏感信息能否被读出，设备会不会因此失去响应，以及 WAN 侧能不能访问这个端口。在这些没有证据之前，比较准确的说法是：TCP 1900 上的 HTTP 管理接口异常暴露，是一块潜在攻击面。不要写成 RCE，也不要写成已经证实的认证绕过。

## 后面值得看的三个问题 ⚠️

第一个是 stok 到底验不验。管理接口把令牌放在路径里，不代表每个请求都会对一下会话。如果一个明显无效的令牌仍能读配置或改配置，那才是认证问题。现在只知道这种路径会被接受，不知道后面的校验结果。

第二个是有没有不登录就能用的管理接口。路径长成 `/stok=.../...` 只能说明风格像管理 API。要等把浏览器里真实的管理请求对上之后，才能判断哪些调用必须有合法管理员会话，哪些在没有会话时也有响应。没有这条对照，就不能说存在未授权访问。

第三个是网络诊断。路由器里常见 Ping、Traceroute、DNS 测试、WAN 测试。这类功能的风险不在于“有 Ping”，而在于用户填的地址或参数会不会原样进到系统命令或内部调用。有没有严格校验，要看固件里的处理，不能从“页面上有这个按钮”推出来。

## 接下来怎么把影响定下来

下一步还是在这台自己的设备上做，顺序大致是：先记下硬件版本和固件版本，再确认 TCP 1900 上是哪个进程在听。然后用浏览器把正常登录后的请求抓下来，整理真实的 HTTP 接口，看 stok 在什么时候生成、什么时候失效。诊断接口只在弄清参数去向之后再判断有没有注入一类的问题。需要看实现时，再对这份固件做解包，用 Ghidra 对上 HTTP 处理函数。

只有在能够说明「输入没有经过应有的校验，并且落到了敏感操作上」之后，才适合写成正式的漏洞说明，补上影响版本、复现条件、影响范围和修复建议。在那之前，这篇只作为研究记录。

本研究只针对本人拥有并控制的 TL-XDR3010，目的是了解嵌入式设备上的 HTTP 服务和会话机制，不涉及他人的设备。
